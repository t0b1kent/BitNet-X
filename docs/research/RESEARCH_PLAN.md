# BitNet-X Research: технический план (черновик 1, 2026-11-17)

Продолжает `docs/experiments/PLAN.md` (ветка `bx/experiment-plan`, PR №12): принцип «движок ≠ модель», метрики и правило сравнения оттуда остаются в силе. Здесь добавлены: диагностика причин ошибок (E0), привязка E1–E3 к гипотезам H1–H3, критерии решений, оценка ресурсов.

## 0. Цель

Не самый быстрый BitNet, а ответ на вопрос: **почему маленькая модель уступает большой и можно ли убрать часть этого разрыва организацией вычислений и обучения, не наращивая параметры**. Модель-основа: BitNet b1.58 2B-4T (тернарные веса). Каждую гипотезу проверяем отдельно, потом (возможно) комбинируем.

| | гипотеза | эксперимент |
|---|---|---|
| H1 | повторное применение общих блоков (рекурсия) улучшает рассуждения при тех же параметрах | E1 |
| H2 | тернарное там, где достаточно, повышенная точность только там, где нужно | E2 |
| H3 | обучение на проверяемой обратной связи (тесты, компилятор) даёт переносимое умение планировать и исправлять | E3 |
| (диагностика) | в чём именно слабость: знания, планирование, арифметика, самопроверка, вычислительный бюджет | **E0** |

## 0.1 Главный вопрос (уточнён проектом 2026-11-17)

Не «взять сжатую большую модель», а **понять, почему силу нельзя сразу заложить в маленькую модель, и научиться это делать**. Что известно о механизмах (метки: проверено поиском / по памяти):

1. **Оптимизация.** Большая сеть легче находит хорошее решение: в ней есть малая подсеть, которая при исходной инициализации обучается до той же точности, а та же малая сеть, обученная с нуля, часто не доходит (гипотеза лотерейного билета, [Frankle, Carbin, arXiv 1803.03635](https://arxiv.org/abs/1803.03635); проверено). Есть контрпример для структурного прунинга (Liu и др., 2018: обучение с нуля не хуже), то есть эффект не универсален.
2. **Сигнал обучения.** Учитель даёт не один верный токен, а всё распределение (дистилляция; Hinton и др., 2015, по памяти). У Qwen3 дистилляция малых моделей по логитам больших заметно лучше RL ([arXiv 2505.09388](https://arxiv.org/abs/2505.09388), проверено). При уже готовом учителе дистилляция выигрывает у обычного обучения до бюджета, который растёт с размером ученика ([Distillation Scaling Laws, ICML 2025](https://arxiv.org/abs/2502.08606), проверено по аннотации).
3. **Ёмкость знаний.** Около 2 бит знаний на параметр (Allen-Zhu, Li): для фактов предел жёсткий. Для рассуждения наш E0b показывает обратное: при поданных фактах 2B решает цепочки из 3 шагов без ошибок.
4. **Объём данных и вычислений.** BitNet 2B4T видел 4T токенов, малые Qwen обучены в семействе, предобученном на 36T, плюс дистилляция.
5. **Наблюдение E0b-2.** Малая модель очень чувствительна к лишнему в контексте (≈ 10 фактов вместо 2–3: с 90–100 % до 70 %).

**Где может быть наш вклад** (гипотезы, каждая с проверкой):
* (a) заложить силу **без большого учителя**: заменить его сигнал тем, что есть у нас бесплатно: проверяемые задачи (тесты), генераторы задач и фактов с известными ответами, самосогласованность. Мера: насколько закрывается разрыв с моделью того же размера, обученной с учителем;
* (b) **перепараметризация только на время обучения**: обучать «широкую» форму, которая после обучения точно сворачивается в маленькую (идея ExpandNets / RepVGG для свёрточных сетей, по памяти); для тернарных языковых моделей я такой работы не нашёл (поиск не проводился, проверить);
* (c) глубина без параметров (H1, рекурсия), уже с обучением;
* (d) обучение устойчивости к лишнему контексту (E0b-2/E0b-3 дают данные бесплатно).

**Роль сравнения BitNet 2B против Ternary Bonsai 2 2B.** Обе модели тернарные и одного размера; Bonsai 2 2B получена из Qwen3.5-2B, то есть из такой же маленькой модели, обученной другим рецептом (больше данных, дистилляция от больших учителей). Разница между ними — это **сколько силы рецепт обучения закладывает в ту же маленькую сеть**: количественный ориентир для (a). Это не предложение сменить основу.

## 2. Метрики и правила (дополнения к PLAN.md)

* Качество: pass@1, pass@k (несмещённая оценка), доля задач, решённых после обратной связи; доверительный интервал Уилсона 95 %; сравнение режимов на одних задачах парным тестом (МакНемара).
* Вычисления: сгенерированные токены, токены промпта, FLOPs/токен (∝ число выполненных слоёв), задержка (отдельно prefill и decode), пиковая память.
* **Сравнение при равном бюджете**: любой метод с дополнительными вычислениями сопоставляется с независимой выборкой того же числа токенов (`summarize.py` считает это из режима B).
* Энергия: `powermetrics` на Mac требует sudo, пароль я не ввожу: либо пользователь запускает сам, либо энергию на Mac не заявляем. На rega: `nvidia-smi` для GPU; для CPU нужен счётчик, который надо проверить.
* Данные: задачи генерируются по seed (`research/tasks/gen_tasks.py`), чужих датасетов нет, контаминации нет. Dev-набор `dev_100.jsonl` (seed 1) для разработки и подбора промптов; **закрытый набор** `test_sealed_100.jsonl` лежит вне репозитория, только для чтения, в репозитории только хеш (`research/tasks/sealed_manifest.json`); открывается один раз для финального сравнения замороженного метода. Закрыт от подбора, не от меня: я его сгенерировал.
* Критерий переноса (пожелание проекта): улучшение должно держаться на **новых семействах алгоритмов**. Для этого в E3 обучаем на части семейств, проверяем на отложенных (в генераторе 10 семейств).

## 3. Эксперименты

### E0. Диагностика причин ошибок (инфраструктура готова, базовый прогон идёт)

100 задач dev-набора, 10 семейств (арифметика, композиция, строки, сканирование, префиксы/суффиксы, классический алгоритм, симуляция стековой машины, ДП на сетке, нестандартная система счисления, обход графа). Режимы: A один ответ; B пять независимых попыток; C подсказка алгоритма; D обратная связь по трём публичным примерам, до 3 раундов; E рассуждение (до 5 шагов) перед кодом. Каждый ответ исполняется в песочнице на 25 скрытых тестах; для неудач ведётся таксономия: нет кода, синтаксис, нет функции, исключение, таймаут, неверный ответ.

Как читать (критерии заданы заранее; n = 100, доверительный интервал порядка ±10 п.п., поэтому значимыми считаем разницы ≥ 10 п.п. по парному тесту):

| сравнение | если выигрыш | значит |
|---|---|---|
| C − A | ≥ 10 п.п. | узкое место в выборе алгоритма/планировании, а не в написании кода |
| D − A и D против выборки при том же бюджете | D выше выборки | модель умеет использовать обратную связь (самопроверка есть) |
| D ≈ выборка при том же бюджете | | обратная связь не лучше повторной генерации |
| E − A | ≥ 5 п.п. | свободное рассуждение помогает без обучения; иначе нужен обученный механизм (H1/H3) |
| B pass@5 − A | большой | верхняя граница для любого верификатора/выбора лучшего |
| провалы по семействам | концентрация в simulation/DP | длинные зависимости и арифметика, а не знания |

### E1. H1: минимальный эксперимент на исходной модели (без обучения)

Зонд «петля блока»: повторить непрерывный блок слоёв [i..j] k раз, каждая копия со своим KV-кэшем (как будто модель глубже). Реализация без правок движка: скрипт делает из официального GGUF новый GGUF, где тензоры `blk.i..j` продублированы и перенумерованы, а `block_count` увеличен; Metal-путь и проверенные ядра работают как есть. Сетка: длина блока ∈ {3, 5, 10}, положение ∈ {ранние, средние, поздние}, k ∈ {2, 3}.
Измеряем: перплексию (`ppl_small.txt` и больший текст), pass@1 по режиму A на dev, сдвиг таксономии ошибок.
Контроли при равном бюджете: (1) исходная модель; (2) выборка k попыток с отбором по публичным тестам (тот же бюджет FLOPs/токенов); (3) режим D.
Ожидание до измерения (чтобы не подгонять): для большинства блоков перплексия ухудшится; интересна величина эффекта по положению и есть ли блок, где pass@1 растёт вне доверительного интервала при ≤ +50 % FLOPs.
**Успех**: прирост pass@1 вне доверительного интервала при ≤ +50 % FLOPs и выше выборки того же бюджета. **Отрицательный результат** фиксируем так же подробно.
Фаза 2 (только если фаза 1 даёт сигнал): лёгкие обучаемые добавки на итерацию (LoRA на каждый проход, идея Relaxed Recursive Transformers) и короткое дообучение на задачах генератора; отдельный план по ресурсам (см. §4).

### E2. H2: карта чувствительности

Для каждого слоя и матрицы заменить тернарные веса на BF16-мастер (он у нас есть) и/или поднять точность активаций; измерить ΔPPL и Δpass@1 на эквивалентный прирост памяти. Первый заход через PyTorch с имитацией квантования на rega (CPU); потом смешанный GGUF. Результат: какие 10–20 % операций дают основную часть качества; затем решение, стоит ли динамический выбор точности (идеи BitNet a4.8/v2 известны). Блокер: пока нет эквивалентной по PPL GPU/PyTorch-реализации, см. открытые проблемы.

### E3. H3: обучение на проверяемой обратной связи

Отбор по тестам (rejection-sampling fine-tuning) или предпочтения из пар «прошёл/не прошёл» на семействах 1–7, проверка на семействах 8–10 и на закрытом наборе: переносится ли умение на **новые типы алгоритмов**. Прецедент RLEF означает, что новизной будет именно проверка переноса и учёт энергии, а не сам метод. Требует обучения: см. ресурсы.

Оценка длительности (по факту первого прогона: режим A на 100 задачах ≈ 17 мин на загруженном Mac, часть ответов упирается в лимит 600 токенов): E0 целиком (A, D, C, E, B) ≈ 2,5 ч; закрытый набор столько же; сетка E1 из 18 вариантов × режим A ≈ 5 ч на одной машине (быстрее, если делить между Mac и rega); режим B (5 образцов) стоит как пять режимов A. Инференс-эксперименты (E0, E1, E2-первый заход) умещаются в Mac и rega. **Обучение** (E1-фаза 2, E3): 2B с LoRA в BF16 (≈4.8 ГБ + активации) теоретически входит в 32 ГБ Mac, но нужны MLX или PyTorch (скачивание), и это часы на прогон; на rega GPU мало свободной памяти, CPU медленен. Обучение с нуля возможно только для моделей порядка ≤100M. Это ограничение надо обсудить до фазы 2.

## 5. Открытые проблемы, которые блокируют часть плана

1. **GPU-стенд не эквивалентен эталону**: PPL 7,38 против 6,43 (Metal 6,4292 и x86 CPU 6,4323 между собой совпадают до 0,01 по каждому блоку). Причина не найдена; исключены токенизация и точность остаточного потока. План локализации: сравнить логиты и активации по слоям с CPU-эталоном на одном и том же входе, начиная с логитов, RoPE, внимания, RMSNorm, квантования активаций и преобразования весов. Не тратить недели: основной путь это Metal.
2. **Шаблон чата в официальном GGUF не совпадает с шаблоном оригинальной модели** (`Human:`/`BITNETAssistant:` и лишний EOS после приглашения ассистента против `Role: текст<|eot_id|>` и `Assistant: `); через `/v1/chat/completions` модель теряет формат и выдаёт бессвязный текст. Мы используем формат оригинала через `/completion`. Это надо проверить и оформить отдельным PR/issue.
3. Чистый upstream на x86 считает неверно (PPL 71,8): какой из наших патчей это исправляет, не изолировано.
4. Патченый x86-путь на prefill медленнее чистого примерно на 10 %: не исследовано.

## 6. Не делаем сейчас

Большую оптимизацию Metal (53 ток/с достаточно для исследования качества); объединение H1, H2, H3; изменение весов без отдельного плана; заявлений о превосходстве над Windows или о новизне без измерений и обзора; трогать vLLM на rega.

* При равном бюджете токенов D (368 токенов) проигрывает трём независимым образцам (40,4 %), E (228) примерно равен двум (35,3 %).
* По шаблонам: всегда решаются `digit_arith`, `string_rule`, `longest_run`; **ни в одном режиме, включая pass@5, не решены** `bfs_order`, `grid_paths`, `stack_machine` (кроме 1 из 10 с подсказкой).
* E: план перед кодом чинит пропуск условия (`filter_map` 0 → 9 из 10), но закрепляет неверный план (`longest_run` 10 → 0: «считать равные соседние пары»); проверено по ответам.

Что надёжно при 10 шаблонах: (1) есть шаблоны с нулём при любой стратегии, их не исправит самообучение на собственных образцах, нужен внешний сигнал (H5); (2) самоисправление при жадном декодировании бесполезно; (3) выборка с отбором даёт порядка +6…10 п.п. Числа по режимам с интервалами шире ±25 п.п. как выводы не используются.

### E0b-2: как отбирать факты (те же 150 вопросов; ориентиры: oracle 91 %, все 117 фактов 39 %)

| тип | поиск по словам (6 фактов) | пошаговый lookup (модель просит факты) | модель сама копирует нужные факты |
|---|---|---|---|
| 1 шаг | 30/30 | 30/30 | 5/30 |
| 2 шага | 0/30 | 9/30 | 1/30 |
| 3 шага | 7/30 | 7/30 | 2/30 |
| подсчёт | 22/30 | 21/30 | 0/30 |
| кто старше | 14/30 | 22/30 | 26/30 |
| всего | 73/150 = 49 % | **89/150 = 59 %** | 34/150 = 23 % |
| доля нужных фактов, попавших в контекст | 65 % | 90 % | 29 % |
| точность, когда все нужные факты есть | 56/64 = 88 % (6 фактов) | 86/122 = **70 %** (≈ 10 фактов) | 28/28 = 100 % (≈ 1 факт) |

Разбор (проверено по логам): (1) поиск по словам промахивается на 2–3 шагах, потому что имени наставника нет в вопросе; когда факты найдены, точность близка к oracle; (2) при пошаговом поиске модель плохо управляет поиском: в 100 из 150 вопросов израсходовала все 3 запроса, на 3 шагах нашла лишь 57 % нужных фактов; (3) **главное: даже когда все нужные факты есть, около 10 фактов вместо 2–3 роняют точность с ≈ 90–100 % до 70 %**, а на 2 шагах до 30 %. Вывод для H4 и идеи «научить отбору»: нужен **точный** отбор (минимум лишнего), и управлять им должна не сама модель, а внешний механизм или отдельно обученный отборщик; данные для обучения отборщика генератор выдаёт бесплатно (нужные факты известны). Оговорка: игрушечный мир, один синтаксис, вопросы по шаблонам, поэтому разбор вопроса на шаги здесь тривиален, в реальном тексте он сложнее.

**Ответ на главный вопрос, насколько он уже измерен.** Тернарный формат не потолок: при тех же 1,15 ГБ и той же скорости в сеть помещается в 2 раза больше решённых задач по коду и устойчивый отбор фактов. Bonsai 2B с телом на треть меньше BitNet не хуже по коду и устойчивее к лишним фактам, когда рассуждает. Проверка: дообучение BitNet (BF16-мастер есть) на наших задачах при равном бюджете токенов двумя способами, только верные решения против решений учителя с открытыми весами (Bonsai 4B, Apache-2.0); мера: прирост на отложенных шаблонах на токен обучения. Нужен стек обучения (согласовать пакеты до скачивания).

### E0b-4: почему модели не могут посчитать людей по 117 фактам и как это исправить (2026-11-18)

**Диагноз по сохранённым ответам E0b-3 (вопросы «сколько людей живёт в X», k = 2…5):**
* BitNet не складывает больше трёх даже по чистым фактам: при одних нужных фактах k = 2–3 всегда верно (13 из 13), k = 4–5 в 3 из 17 и всегда недосчёт. Предел сложения.
* Bonsai 4B складывает без ошибок (30 из 30 по чистым фактам), но на всех 117 фактах недосчитывает в 29 из 30: теряет нужные строки в длинном списке. Провал поиска, а не арифметики.
* Bonsai 2B при лишних фактах пересчитывает (включает чужих).

Литература даёт тот же механизм. Softmax-внимание нормирует веса до суммы 1, поэтому даёт долю подходящих позиций, а не их число ([2310.08661](https://arxiv.org/abs/2310.08661), [2407.15160](https://arxiv.org/abs/2407.15160)). С ростом контекста максимум внимания на нужной позиции падает («затухание внимания», [Scalable-Softmax, 2501.19399](https://arxiv.org/abs/2501.19399)). У моделей есть «надёжная зона» счёта, за которой точность обрывается резко, а не постепенно ([Stanford, «Counting as a minimal probe»](https://fanlab.stanford.edu/wp-content/papercite-data/pdf/dai2026reliability.pdf)). Разбиение на подзадачи внутри зоны с последующим сложением держит точность там, где обычный подсчёт ломается после ≈ 30 предметов ([2601.02989](https://arxiv.org/abs/2601.02989)).

**Раунд 1 (`qa_count.py`, `run_count.sh`, `research/results/cmp/count/<модель>/summary.md`), верно из 30 при 0 / 30 / всех ≈ 115 лишних фактах:**

| способ | BitNet | Bonsai 2B | Bonsai 4B |
|---|---|---|---|
| сразу ответ | 16 / 3 / 5 | 30 / 10 / 2 | 30 / 13 / 1 |
| нумерованный список, число от модели | 12 / 0 / 0 | 28 / 8 / 2 | 18 / 8 / 9 |
| куски по 10 фактов, сложение кодом | 16 / 9 / 1 | 28 / 1 / 3 | 30 / 24 / **27** |

Стек: MLX 0.32.4 и mlx-lm 0.32.2 в отдельном окружении `~/Developer/MicrosoftAI/.venv-train`. Для двухшаговых вопросов та же картина (0,96 → 0,83 → 0,64 → 0,28; полнота 0,90 → 0,23). Поиском заняты несколько голов в средних слоях 14–17 (L16H13, L16H8, L16H6, L17H4, L17H17: около 1 % из 600), как «retrieval heads» в литературе ([2404.15574](https://arxiv.org/abs/2404.15574): меньше 5 % голов, их удаление ломает извлечение). Вывод: модель знает, куда смотреть (на 117 фактах голова в 10 раз избирательнее случайного), но softmax размазывает внимание по сотне лишних фактов, и на нужные остаётся около 30 %. Это прямой механизм провала подсчёта и цепочек на длинных списках.

**Линза по слоям для двух формулировок судьи** (40 фактов о городе, 20 других; доля, где верный ответ первый по вероятности):

| прямая («в каком городе? одним словом»), город | 37 из 40 | «none» 0,17 | «none» 0,95 | город 0,93 | город 0,97 | город 0,93 |
| обе, факт не о городе | 20 из 20 и 20 из 20 | | «none» 1,00 | | | «none» ≈ 1,00 |

Вывод: правильный город внутри модели есть и при условной формулировке (на слое 27 он первый в 57 % случаев), но последние два слоя перебивают его на «none». Знания не не хватает: последние слои неверно применяют условие. Значит, чинить надо поздние слои обучением на формулировках, без роста размера.

**Почему «≈ 2 бита знаний на параметр» и что с этим делать.** Число Allen-Zhu и Li ([2404.05405](https://arxiv.org/abs/2404.05405)) измерено для 16-битных моделей: они используют около 2 из 16 бит; int8 ёмкость сохраняет, int4 снижает (по вторичному пересказу до ≈ 0,7, не сверено). Для тернарного веса есть жёсткий математический предел: 3 значения несут не больше log₂3 ≈ 1,58 бита, то есть BitNet 2,4B хранит не больше ≈ 3,8 Гбит ≈ 475 МБ произвольной информации (принцип Дирихле, а не железо). Сколько из этого BitNet реально использует, я не нашёл: можно измерить на синтетических биографиях. Обходов предела три: факты, подчиняющиеся правилам, хранить как правило; несжимаемые факты вынести из весов в память с точным доступом (таблица мира 0,7 КБ против 72 МБ кеша; DeepSeek Engram ([2601.07372](https://arxiv.org/abs/2601.07372)): таблица на 100B параметров в памяти хоста с замедлением < 3 % по словам авторов); веса оставить под навыки (разбор, логика).

**Почему большие таблицы трудны в дата-центре и почему у нас иначе.** На GPU с батчем из многих пользователей одно чтение веса используется сотнями токенов (расчёт упирается в вычисления); таблица наоборот: каждому токену нужны свои строки, общего чтения нет, всё упирается в пропускную способность памяти (Meta: слои памяти «почти полностью ограничены пропускной способностью», понадобились свои ядра и разнесение по GPU, [2412.09764](https://arxiv.org/abs/2412.09764); у ByteDance памяти на product keys хуже MoE, понадобился UltraMem, [2411.12364](https://arxiv.org/abs/2411.12364)), а таблицы на сотни миллиардов параметров не помещаются в память одной GPU. На Mac один пользователь, decode и так упирается в чтение 1,18 ГБ весов на токен, а поиск в таблице читает килобайты; память общая для CPU и GPU, таблица может лежать в RAM или на SSD, адреса известны заранее, их можно подгружать параллельно. То, что в дата-центре недостаток, у нас преимущество: объём знаний растёт с объёмом памяти, а не с байтами на токен.

### Карта идей: две разные задачи (2026-11-18)

Измерения разделили провалы малых моделей на две задачи с разными рычагами. Заострение внимания или таблица решают первую и не объясняют, почему каждое новое поколение Qwen 27B умнее предыдущего: это вторая.

**Задача A: пользоваться контекстом (отбор нужного среди лишнего).** Механизм измерен внутри: головы поиска в слоях 14–17 размывают внимание по сотне лишних фактов.
1. Таблица, прочитанная один раз (сделано, 150 из 150 у всех трёх моделей): сейчас внешняя, прототип нативной памяти.
2. Без обучения, в движке: заострение отдельных голов (проверено, **не помогает**, см. ниже), масштаб логитов от длины (Scalable-Softmax, [2501.19399](https://arxiv.org/abs/2501.19399)), разреженное внимание top-k или с порогом в головах поиска ([2601.12145](https://arxiv.org/abs/2601.12145)).
3. С дообучением: дифференциальное внимание (разность двух softmax, [2410.05258](https://arxiv.org/abs/2410.05258)), stick-breaking ([2410.17980](https://arxiv.org/abs/2410.17980)); у Softpick ([2504.20966](https://arxiv.org/abs/2504.20966)) на длинном контексте нерешённое «занижение» оценок.
4. Нативная память чтения и записи: Titans ([2501.00663](https://arxiv.org/abs/2501.00663)), Memory Layers ([2412.09764](https://arxiv.org/abs/2412.09764)), Engram ([2601.07372](https://arxiv.org/abs/2601.07372)). Для устройства выгоднее, чем для дата-центра: на токен читаются килобайты таблицы при 1,18 ГБ весов.
5. Обучить процедуру: модель сама делает то, что сейчас делает обвязка (судья по фактам, запись в таблицу).

**Задача B: что вложено в веса (почему новые поколения той же величины умнее).**
1. Математика хранения (измерено): тернарные веса BitNet заполнены на 98 % (энтропия 1,560 бита на вес из 1,585; доли −1 / 0 / +1 = 0,289 / 0,422 / 0,289; `research/results/inside/bitnet/weight_entropy.md`). Больше информации в те же веса не положить; упаковка по основанию 3 (5 весов в байт) уменьшает хранение тернарных слоёв с 521 до 417 МБ, то есть ускоряет decode (байт на токен меньше), но знаний не добавляет.
2. Эффективность обучения (Allen-Zhu, Li [2404.05405](https://arxiv.org/abs/2404.05405)): 2 бита на параметр требуют около 1000 показов факта, при 100 показах примерно вдвое меньше; «мусорные» данные снижают ёмкость полезного знания до 20 раз, приписанный к тексту источник (например, `wikipedia.org`) возвращает заметную часть (числа по пересказам, сверить).
3. Разнообразие формулировок в данных ([2309.14316](https://arxiv.org/abs/2309.14316)): без пересказов факт запоминается, но не извлекается (0 % после любого дообучения); с пересказами знание хранится у имени сущности и извлекается. Это та же «привязка к варианту», что мы видели у судьи, только в обучении: разные варианты в данных дают одно общее представление в весах.
4. Синтетические данные: EntiGraph ([2409.07431](https://arxiv.org/abs/2409.07431)) из 1,3 млн токенов делает 455 млн разнообразного текста, и дообучение на нём даёт 80 % выигрыша, который даёт поиск по исходным документам.
5. Учитель: дистилляция от большой модели (отчёт Qwen3; по пересказу Densing Law, Gemma-2-9B, дистиллированная из 27B, повысила плотность способностей, а обычные сжатия её понижают). Плотность способностей лучших открытых моделей удваивается примерно каждые 3,3 месяца ([2412.04315](https://arxiv.org/abs/2412.04315)).
6. Правила вместо фактов: закономерное знание хранится как правило, произвольное выносится в память с точным доступом.

**Заострение голов поиска без обучения (`inside.py sharpen`, `research/results/inside/bitnet/sharpen.md`).** Логиты выбранных голов умножались на τ (через масштаб запроса), BitNet, верный первый токен ответа из 30 на ячейку (метрика по первому токену мягче полной: у похожих городов общий первый токен):

|---|---|---|---|---|
| без изменений | 1 | 4 / 13 / 4 | 2 / 15 / 3 | 41 |
| 7 голов поиска | 1,5 / 2 / 3 | 5 / 13 / 6 … 4 / 15 / 4 | 2 / 14 / 3 … 2 / 12 / 2 | 43 / 42 / 39 |
| все 80 голов слоёв 14–17 | 1,5 / 2 / 3 | 4 / 14 / 3 … 7 / 14 / 6 | 2 / 12 / 3 … 2 / 12 / 4 | 38 / 42 / 45 |

Вывод: заострение отдельных голов меняет результат в пределах шума (±4 из 180), заострение всех голов ломает модель. Причина видна из замера внимания: на 117 фактах лучшая голова ставит нужные факты в свой top-k лишь в 38 % случаев, то есть ошибается не только «мягкость», но и сама оценка соответствия запроса и ключа; заострение усиливает и ошибки. Чинить отбор надо обучением (точнее сопоставление запроса и ключа в головах поиска) или структурой (таблица, память).

**Следующие опыты (дёшевые, на Mac):** (а) ёмкость тернарной модели: маленькие тернарные модели с нуля на синтетических биографиях, сколько бит на параметр они набирают и как это меняют пересказы, метка источника и учитель (опубликованного замера для тернарных моделей я не нашёл); (б) дообучение последних слоёв BitNet на многих формулировках (лечит «none» поверх верного города); (в) нативная память для малой модели.

## 8. Две дорожки: скорость и интеллект (уточнение проекта, 2026-11-17)

Решение проекта: не принимать «этого ещё никто не делал» за аргумент ни за, ни против. Идём двумя дорожками, которые усиливают друг друга: быстрая дешёвая генерация нужна и самой модели (поиск, данные для дообучения).

### Дорожка S: скорость (использовать не 31 % пропускной способности)
Каждый шаг проходит ворота: перплексия не меняется (6,4292 в допуске), `scripts/run_tests.sh` зелёный, A/B на свободной машине, разбор «мс на токен» по операциям.
* **S0** измерить реальный потолок: Metal-замер потоковой пропускной способности (без него «31 %» считается от паспортных 200 ГБ/с).
* **S1** профиль графа decode: сколько запусков ядер и сколько GPU-времени у каждой операции (оценка из PR №14: ≈ 12 мс графа и ≈ 3 мс квантования активаций при ≈ 5 мс матвека).
* **S2** слияние мелких операций (RMSNorm + квантование, RoPE + запись в KV, relu²·умножение + норма + квантование), меньше барьеров, ядро lm_head (56 % трафика).
* **S3** параллельные последовательности и спекулятивное декодирование: при памяти как узком месте несколько последовательностей в батче почти не дороже одной; быстрый матричный путь (710 ток/с) проверяет сразу несколько токенов-кандидатов. Источник кандидатов без обучения: поиск n-грамм по контексту (хорошо для кода). Предупреждение из литературы: на Apple Silicon многотокенное предсказание местами замедляет декодирование, поэтому только замер.
* **S4** меньше байт: lm_head в 8 бит меняет числа и требует PPL-ворот; решение отдельное.
Ожидание до измерения (гипотеза): S2 даёт порядка 80–110 ток/с; выше только вместе с S3.

### Дорожка I: интеллект
* **I0 = E0** диагностика (идёт).
* **I1 поиск с проверкой**: выборка нескольких решений (до 32, батчем: чтение весов делится между последовательностями) и отбор по 3 публичным примерам плюс согласованность решений с тестами, написанными самой моделью (CodeT). **Верификатор на этапе вывода слабый**: скрытые тесты это оценка, а не инструмент; поэтому отчитываемся отдельно по «selected@1» (доля прохождений скрытых тестов у выбранного решения) и по оракульному pass@k (верхняя граница). Кривая pass@k по несмещённой оценке.
* **I2 «поиск в веса»**: быстро сгенерированные решения, отобранные тестами, используются для дообучения (rejection-sampling fine-tuning / expert iteration); проверка на отложенных семействах и закрытом наборе. Для малых моделей 1,5–3B обучение с проверяемыми наградами работает на практике (см. §9); для тернарной основы данных я не нашёл. Нужен стек обучения (MLX или PyTorch на Mac: скачивание, нужно ваше подтверждение с точным списком пакетов и размерами).
* **I3 рекурсия**: пробы без обучения на PPL дали отрицательный результат; pass@1 для двух вариантов после E0; фаза с обучением только при сигнале.
* **I4 карта точности (E2)**.

**Гипотеза проекта (проверяемая, не обещание):** у тернарной модели decode упирается в чтение весов, поэтому генерация нескольких кандидатов в батче и повтор уже загруженных весов относительно дёшевы; значит «поиск с проверкой плюс перенос найденного в веса» может дать больше качества на джоуль, чем у плотных моделей. Проверка: масштабирование агрегатной скорости от числа параллельных последовательностей (S3) и pass@k на токен (I1).

### H4 (добавлена по указанию проекта): знания можно вынести из весов
Тезис проекта: вес нужен для хранения знаний; если хранение и извлечение сделать сверхэффективными, большой вес не нужен. Что известно: ёмкость знаний модели около 2 бит на параметр и сохраняется при int8 (Allen-Zhu, Li, [ICLR 2025](https://arxiv.org/abs/2404.05405); результат для 4 бит в моей выдаче не подтверждён). Значит, сжатие знаний внутри весов упирается в информационный предел; обойти его можно, **вынеся факты из весов**: поиск по внешнему индексу (Atlas, [JMLR 2023](https://jmlr.org/papers/v24/23-0037.html): модель в 50 раз меньше обошла 540B на Natural Questions в few-shot, по самим авторам) или таблица знаний, отделённая от вычислений (DeepSeek Engram, январь 2026: по вторичному пересказу, таблица лежит во внешней памяти с потерей скорости менее 3 %, лучшая доля около 20–25 % разреженных параметров; цифры не сверены с первоисточником).
Наши данные: на коде главный провал не в знаниях (подсказка алгоритма 44 % против 37 %; ошибки в симуляции, ДП, обходе графа). Чтобы разделить «знание» и «рассуждение» измерением, сделан **E0b**: выдуманный мир (имена, города, профессии, которых нет в обучении), вопросы в 1, 2, 3 шага, подсчёт и сравнение; три условия: closed (без фактов; чем модель «знает» этот мир: пол угадывания), oracle (только нужные факты), open (все факты мира). Чтение: oracle высокий на всех шагах означает, что при бесплатных знаниях маленькой модели хватает и узкое место это хранение знаний; oracle падающий с числом шагов означает, что узкое место это рассуждение, а не хранение.
Следующий шаг при высоком oracle: прототип «знания вне весов» (индекс фактов и извлечение), мера: точность на вопросах о фактах против размера модели.

### H5 (из литературы, 2026-11-17): навыки переносятся от большой модели к малой
Почему малые Qwen сильнее: Qwen3 предобучен на 36T токенов, малые модели получены дистилляцией «сильный → слабый» (ответы учителя, затем выравнивание логитов по Qwen3-32B/235B); авторы пишут, что для малых моделей дистилляция заметно лучше RL ([arXiv 2505.09388](https://arxiv.org/abs/2505.09388)). BitNet 2B4T: 4T токенов, SFT и DPO, без дистилляции и без RL на рассуждениях (по пересказам отчёта [arXiv 2504.12285](https://arxiv.org/abs/2504.12285)). Эмпирически «плотность способностей» лучших открытых моделей удваивается примерно каждые 3,3 месяца ([Densing Law, arXiv 2412.04315](https://arxiv.org/abs/2412.04315)), то есть рост ума при том же размере идёт от данных и рецепта обучения. Низкая точность обучения уменьшает «эффективное число параметров» ([Scaling Laws for Precision, arXiv 2411.04330](https://arxiv.org/abs/2411.04330)); контролируемого сравнения тернарной и bf16 модели 2B на одних данных я не нашёл.
Следствие: работающее «сжатие» это сжатие **навыков** большой модели в малую (дистилляция), а не битов весов. Для шаблонов с нулём при любой стратегии это единственный внешний сигнал. План: учитель с открытыми весами и разрешающей лицензией решает наши задачи, тесты отбирают верные решения, BitNet дообучается на них (дистилляция последовательностями: токенизаторы разные, логиты напрямую не сопоставить). Ответы Claude как обучающие данные не используем: условия Anthropic ограничивают использование ответов для обучения моделей. Именно наш открытый вопрос: сохраняется ли выигрыш при дообучении с тернарным квантованием в прямом проходе (BF16-мастер есть локально).
Нужно решение: (1) контрольная плотная малая модель сопоставимого размера в байтах (ответит, какие провалы тернарные, а какие от рецепта); (2) учитель. Оба требуют скачивания; конкретные файлы и размеры согласовать до загрузки.

### Готовое подтверждение идеи «веса сильной модели → тернарные»: PrismML Bonsai (2026-11-17)
PrismML выпускает тернарные и 1-битные модели, полученные из сильных плотных моделей Qwen (Apache-2.0): метод по пересказам «повёрнутый базис весов + групповые FP16-масштабы», без описанного шага дистилляции. Заявление производителя (независимых проверок не найдено): Ternary Bonsai 2 27B из Qwen3.8-27B сохраняет 98,2 % среднего по тестам при ≈ 5,9 ГБ против 53,8 ГБ FP16 ([пересказ](https://aiweekly.co/alerts/prismml-compresses-qwen38-27b-to-593-gb-with-ternary-weights), [PrismML](https://prismml.com/news/ternary-bonsai)). Карточка модификации на rega: MMLU 0,78 у тернарной против 0,83 у Qwen3.8-27B Q4_K_M (не проверено).
Что это значит для нас: «сжать навыки сильной модели в тернарную» уже работает у других; наш BitNet 2B4T (обучен тернарным с нуля, 4T токенов) может быть слабой основой. Решающий контроль при равных параметрах и равных байтах:

### Исправления по независимому обзору (Opus 5.5) и по самопроверке, 2026-11-17

* **Верификатор не идеальный.** Прежняя формулировка «идеальный верификатор» неверна: на новой задаче есть только публичные примеры, они слабый фильтр с ложными срабатываниями. Теперь всегда selected@1 отдельно от pass@k.
* **Эффективный размер выборки мал.** В генераторе каждое семейство это 1–2 структурных шаблона с разными константами (проверено по «отпечатку» эталонного кода), поэтому 100 задач ≈ 10 разных проблем. Интервалы Уилсона в §7 считают задачи независимыми и оптимистичны; по семействам при n = 10 они ±30 п.п., а p ≈ 0,065 по 11 расходящимся парам это шум. Исправление: не больше констант, а **больше разных шаблонов** (цель ≥ 30 семейств, не менее 20 вариаций, выводы на уровне шаблонов).
* **Самоисправление переделать честно.** Нулевой результат D в основном артефакт жадного декодирования: тот же промпт даёт тот же ответ. Нужны: исправления с выборкой, обратная связь с входом, ожидаемым и фактическим выводом, сравнение с k свежими выборками при том же бюджете. Прецедент: самоисправление даёт мало или ничего, если считать добавочные вычисления ([Olausson и др., arXiv 2306.09896](https://arxiv.org/abs/2306.09896)); узкое место в оценке своего кода, а не в самом исправлении.
* **Перенос обучения с проверкой (I2).** Отложенные семейства обязательны, иначе измерим запоминание шаблонов. LoRA на тернарной основе: при слиянии с весами они перестают быть тернарными, раздельно это лишний f16-матмул на каждом шаге; варианты: LoRA только на lm_head или на последних слоях. BF16-веса у нас уже локально (`BitNet-Original/model.safetensors`), скачивать их не нужно.
* **Не тернарная специфика.** Все эксперименты I1–I2 используют то, что decode упирается в чтение памяти, а не то, что веса тернарные. Преимущество именно тернарности (меньше байт, больше места для батча) можно заявлять только в сравнении с плотной малой моделью при равных байтах; для этого нужна вторая модель, то есть скачивание (по согласованию).
* **Пересмотр E1.** Перплексия на обычном тексте не та метрика для рассуждений; оставляем pass@1 для двух вариантов, приоритет низкий.
* **Скорость, `lm_head` (0,66 ГБ из 1,18 ГБ на токен).** Точные способы: батч делит чтение lm_head между последовательностями (самый крупный выигрыш, для I1 бесплатно); отбор словаря на стороне черновика (FR-Spec, [arXiv 2502.14856](https://arxiv.org/abs/2502.14856); VocabTrim, [arXiv 2506.22694](https://arxiv.org/abs/2506.22694)); сертифицированный top-k с запасным полным проходом (в литературе для этого случая не нашёл, не проверено). Меняют распределение: квантование lm_head в q8_0 или q6_K (≈ −0,33 или −0,41 ГБ на токен; по памяти ≈ 1,4–1,6× к decode, перед принятием проверить pass@1, а не только PPL) и постоянное ограничение словаря для кода. По решению проекта квантование lm_head не исследовательский путь: остаётся только инженерной опцией вне повестки.
